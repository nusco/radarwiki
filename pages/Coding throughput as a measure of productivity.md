## Current state (late 2026)

Measuring developers by lines of code is an old mistake, and the industry had mostly learned to avoid it. AI brought it back. In April 2026 the Radar warned against judging AI coding by lines of code and pull requests. By November 2026 the metrics had become stranger: the share of code written by AI, or the number of tokens used, treated as badges of honor. The blip's answer hasn't changed: measure outcomes, with frameworks like DORA, not activity.

## Level 1 — What it is (~10 min)

Activity metrics, like lines of code, pull requests, the AI share of code or tokens, show adoption, not productivity, and turn into bad targets.

- [ ] **~10 min** · Read: [The Radar blip](https://www.thoughtworks.com/radar/techniques/coding-throughput-as-a-measure-of-productivity) (~2 min per version) — read both versions. April 2026 suggests a better leading indicator, first-pass acceptance rate, and November 2026 adds the warning about Goodhart's law.

## Level 2 — Better measures (~35 min)

Learn the measures the blip recommends, and check the ones your organization uses.

- [ ] **~15 min** · Read: [DORA's software delivery performance metrics](https://dora.dev/guides/dora-metrics/) (Nathen Harvey, DORA, updated Jan 2026, ~5 min) — the five metrics, split into throughput and instability. Read "Common pitfalls" carefully: the first one is setting metrics as goals, which is the blip's point.
- [ ] **~20 min** · **Do:** List the metrics your organization uses, or talks about, to judge AI adoption. Mark each one as activity or outcome. For each activity metric, write how a team could game it without delivering anything better. Then pick one outcome metric you'd propose instead.
